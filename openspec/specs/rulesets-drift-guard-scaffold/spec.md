# rulesets-drift-guard-scaffold Specification

## Purpose

Ensures every repo onboarded via `worktrail-repo-init` gets a working, credential-guarded
CI job that catches drift between committed `.github/rulesets/*.json` and GitHub's live
ruleset state, instead of shipping rulesets JSON with nothing verifying it stays applied.

## Requirements

### Requirement: propose scaffolds the drift-guard workflow and its vendored script
`worktrail-repo-init propose` SHALL write `.github/workflows/rulesets_drift_guard.yml` and a
vendored `scripts/ci/rulesets/{rulesets_sync.py,requirements.txt}` into the target repo
whenever `.github/rulesets/*.json` is also being written or already exists, using the same
write-if-absent idempotency as every other file `propose` scaffolds.

#### Scenario: Fresh repo gets the drift guard alongside its rulesets
- **WHEN** `propose` is run against a repo with no existing `.github/rulesets/` directory
- **THEN** `propose` writes `.github/rulesets/protect-*.json`, `.github/workflows/rulesets_drift_guard.yml`,
  and `scripts/ci/rulesets/{rulesets_sync.py,requirements.txt}`, and reports all of them under
  "written"

#### Scenario: Re-running propose does not overwrite an existing drift guard
- **WHEN** `propose` is run against a repo where `.github/workflows/rulesets_drift_guard.yml`
  already exists
- **THEN** `propose` leaves that file untouched and reports it under "skipped"

### Requirement: scaffolded workflow targets the repo's actual branch model
The scaffolded `rulesets_drift_guard.yml`'s `pull_request`/`push` branch triggers SHALL list
exactly the branches `propose` is scaffolding rulesets for (`dev`/`prd` for the 2-branch model,
`dev`/`stg`/`prd` for the 3-branch model), never a hardcoded `main`.

#### Scenario: 2-branch model repo
- **WHEN** `propose` is run with `--branch-model 2` (the default)
- **THEN** the scaffolded workflow's `pull_request.branches` and `push.branches` are exactly
  `[dev, prd]`

#### Scenario: 3-branch model repo
- **WHEN** `propose` is run with `--branch-model 3`
- **THEN** the scaffolded workflow's `pull_request.branches` and `push.branches` are exactly
  `[dev, stg, prd]`

### Requirement: scaffolded workflow mints its token from the existing fleet-wide App
The scaffolded workflow SHALL mint its GitHub API token via `actions/create-github-app-token`
using `vars.RELEASE_NOTES_APP_ID` / `secrets.RELEASE_NOTES_APP_PRIVATE_KEY` -- the same App
identity devops, datalena, and gracefully-giving-back already use -- and SHALL NOT rely on the
default `GITHUB_TOKEN` for the rulesets-check/apply step.

#### Scenario: Workflow generated by propose
- **WHEN** `propose` writes `rulesets_drift_guard.yml`
- **THEN** the job's token-minting step references `vars.RELEASE_NOTES_APP_ID` and
  `secrets.RELEASE_NOTES_APP_PRIVATE_KEY`, and no step in the job uses `secrets.GITHUB_TOKEN`
  to call the rulesets API

### Requirement: missing App credentials produce a clean skip, not a failure
When `vars.RELEASE_NOTES_APP_ID` or `secrets.RELEASE_NOTES_APP_PRIVATE_KEY` are not configured
in the target repo's Actions settings, the scaffolded workflow's job SHALL report a skipped
conclusion for its credential-dependent steps rather than a failing one.

#### Scenario: App not yet installed on a freshly onboarded repo
- **WHEN** the drift-guard workflow runs in a repo where `RELEASE_NOTES_APP_ID` has no value
- **THEN** the steps that mint a token and call the rulesets API report `skipped`, and the job
  as a whole does not fail

### Requirement: apply reports a reminder when App credentials are missing
`worktrail-repo-init apply` SHALL check whether `RELEASE_NOTES_APP_ID` (repo variable) and
`RELEASE_NOTES_APP_PRIVATE_KEY` (repo secret) exist in the target repo, and SHALL print a
one-line reminder to install the App and set them when either is missing.

#### Scenario: apply run against a repo without the App configured
- **WHEN** `apply` runs against a repo where `RELEASE_NOTES_APP_ID` is not set as a repo
  variable
- **THEN** `apply`'s output includes a reminder naming both the App-install step and the
  missing variable/secret

#### Scenario: apply run against a repo with the App already configured
- **WHEN** `apply` runs against a repo where both `RELEASE_NOTES_APP_ID` and
  `RELEASE_NOTES_APP_PRIVATE_KEY` are already set
- **THEN** `apply` does not print the credential reminder
