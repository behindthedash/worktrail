## Context

See proposal.md - Why for motivation. Verified facts that shape this design (grepped
against this worktree's checkout of `src/worktrail/orchestrator/live.py` and
`spawnlib.py`, and `src/worktrail/router/{invocation_context,run_record}.py`):

- Every headless worker child process, regardless of which CLI (`claude`, `codex`,
  `opencode`) or which `live.py` subcommand launches it, funnels through one function:
  `spawnlib.spawn_agent()`. Its nested `build_child_env()` closure is the single
  point where the child's environment dict is assembled — it already has exactly one
  precedent for this shape: an unconditional-if-present passthrough of
  `WORKTRAIL_SKILL_DISPATCH_DEPTH` from the orchestrator's own env into the child's.
- "Dispatch identity" (`dispatch_id`) and the orchestrator's own "run identity"
  (`run_id`, e.g. `full-<timestamp>`, from `read_or_create_run_id`) are two distinct,
  unrelated identity systems today. `run_id` is generated and owned entirely inside
  `live.py`. `dispatch_id` is generated by `router/invocation_context.resolve()`
  (a fresh `uuid4` per top-level call, unless one is passed in) and is the identity
  `worktrail-run-record start --dispatch-id` stamps onto a run record — the same
  value `worktree-conflict`'s `same_dispatch` check compares against. `live.py` does
  call `invocation_context.resolve()` once today (`_detect_default_agent()`, for
  `agent_cli` only), but that call passes no `dispatch_id` and its result is never
  stored — it is a throwaway resolution for a different field, not a source of a
  stable per-run dispatch identity.
- The `full-real` subcommand (`worktrail-live full-real`) is the one worker-spawn
  entry point real orchestrator runs actually invoke, per
  `skills/worktrail-go/references/subagent-prompts.md`'s `full-real` invocation
  line. Other subcommands (`smoke`, `instantiate`, `live-run`, `full`, `spawn-one`,
  `live-run-real`) operate on sample/sandbox fixtures or are ad hoc debugging entry
  points, not the routed production path.
- That `subagent-prompts.md` invocation line does not currently pass any
  `--dispatch-id`-shaped value, and the value it would need
  (`$INVOCATION_CONTEXT_DISPATCH_ID`) is computed by `worktrail-go/SKILL.md` in the
  top-level `/go` session, not automatically available inside the separately
  dispatched subagent whose prompt contains that bash block. Wiring that connection
  is therefore a distinct change from this one (see Non-Goals).

## Goals / Non-Goals

**Goals:**
- Make `WORKTRAIL_DISPATCH_ID` a documented, testable env var that appears in a
  spawned worker's environment whenever a caller supplies a dispatch identity to the
  worker-spawn path, with the exact value supplied.
- Keep the mechanism agent-agnostic (claude/codex/opencode) by adding it at the one
  shared `build_child_env()` choke point rather than duplicating it per-CLI.
- Preserve today's behavior byte-for-byte when no dispatch identity is supplied —
  this is an additive, opt-in parameter, not a behavior change for existing callers.

**Non-Goals:**
- Generating or resolving a dispatch identity from within `live.py`/`spawnlib.py`.
  The value is supplied by the caller; this change only carries it through, per the
  spec's "no identity is invented when none is supplied" requirement. Auto-resolving
  one (e.g. via `invocation_context.resolve()`) would risk minting a value that does
  not match the one already stamped on the run's own run record, which would make
  the eventual conflict-guard hook fail closed on the run's own workers — the exact
  regression this change exists to prevent.
- Updating `subagent-prompts.md` (or any other skill doc) to actually pass
  `--dispatch-id` on the `full-real` invocation. Confirmed above that the value the
  skill would need to pass is not currently in scope for the subagent prompt that
  runs that line — connecting it is a separate, not-yet-scoped change to the
  skill/dispatch layer, not a plumbing change to the orchestrator.
- The devops-repo `worktree-conflict-guard.py` hook (separate repo).
- Threading `dispatch_id` through subcommands other than `full-real` (`live-run-real`,
  `spawn-one`, etc.). They share the same `LiveSpawn`/`spawn_agent` machinery, so
  they can adopt the same constructor/CLI parameter later with no further plumbing
  changes to `spawnlib.py` — but that's speculative flexibility this change does not
  need to add now, since only `full-real` is the routed production path today.

## Decisions

**Add `dispatch_id` as an optional keyword parameter on `spawn_agent`/`spawn_claude_p`,
consumed inside `build_child_env`.** Alternative considered: set
`WORKTRAIL_DISPATCH_ID` at the `LiveSpawn.__call__` level by mutating
`os.environ` before invoking `spawnlib`. Rejected: `os.environ` mutation is
process-global and not thread/async-safe across the orchestrator's concurrent
worker fan-out (multiple `LiveSpawn.__call__` invocations for different tasks run
concurrently), whereas `build_child_env` already builds a fresh per-call dict copy
(`{**os.environ, ...}`) with no shared mutable state.

**Store `dispatch_id` on `LiveSpawn` as a constructor parameter (mirroring `effort`,
`model`), not a per-`__call__` argument.** One dispatch identity applies to an entire
run, not per-task — matching how `model`/`effort`/`tier_map` are already resolved
once at `LiveSpawn` construction and reused for every task worker that instance
spawns. A per-`__call__` parameter would imply (incorrectly) that different tasks in
the same run could carry different dispatch identities.

**Add `--dispatch-id` only to the `full-real` argparse subparser**, not a shared
argument-group helper. `full-real` is the only subcommand this change threads it
through (see Non-Goals); introducing a shared helper for one call site would be
speculative abstraction for a single use.

**No env var when `dispatch_id` is `None`**, rather than a sentinel/empty-string
value. An empty or placeholder value is indistinguishable from a real (if unlikely)
dispatch id to a naive consumer; omitting the key entirely is the unambiguous "not
supplied" signal, consistent with the spec's explicit "do not fabricate" requirement.

## Risks / Trade-offs

- [The env var reaches workers correctly, but no shipped caller ever passes
  `--dispatch-id` yet, so the feature is inert until the separate skill-wiring
  change lands] → Documented explicitly in proposal.md's Out of Scope and this
  design's Non-Goals rather than left implicit, so the follow-up work is visible
  and not mistaken for "already done" once this change merges.
- [A future caller passes a `dispatch_id` that does not match the value the run's
  own run record was started with (e.g., a stale or hand-typed id), which would
  make the eventual conflict-guard hook wrongly treat the run's own workers as
  external] → Out of this change's control: correctness of the value is entirely
  the caller's responsibility, which is why this change deliberately does not try
  to resolve or validate the value itself (see Non-Goals).

## Migration Plan

Purely additive: a new optional parameter, a new optional CLI flag, and one new
conditional environment key. No existing call sites pass `dispatch_id`, so no
existing behavior changes. No rollback concerns beyond a normal revert.
