## Purpose

Ensures every repo onboarded via `worktrail-repo-init` gets a self-contained, credential-free
CI check that catches a `.github/dependabot.yml` ecosystem entry whose configured directory
holds no manifest Dependabot can parse — a misconfiguration that otherwise fails only the
Dependabot Updates job, silently, with no PR check and no branch-protection signal.

## ADDED Requirements

### Requirement: propose scaffolds the manifest check workflow and its vendored script
`worktrail-repo-init propose` SHALL write `.github/workflows/dependabot_manifest_check.yml` and
a vendored `scripts/ci/dependabot/{dependabot_manifest_check.py,requirements.txt}` into the
target repo, using the same write-if-absent idempotency as every other file `propose` scaffolds.
Scaffolding SHALL NOT be conditional on the target repo already having a
`.github/dependabot.yml` — the check exists so that adding one later is safe.

#### Scenario: Fresh repo gets the manifest check
- **WHEN** `propose` is run against a repo with none of these files present
- **THEN** `propose` writes `.github/workflows/dependabot_manifest_check.yml`,
  `scripts/ci/dependabot/dependabot_manifest_check.py`, and
  `scripts/ci/dependabot/requirements.txt`, and reports all three under "written"

#### Scenario: Repo with no dependabot.yml still gets the check
- **WHEN** `propose` is run against a repo that has no `.github/dependabot.yml` at all
- **THEN** `propose` still writes the workflow and the vendored script pair

#### Scenario: Re-running propose does not overwrite an existing check
- **WHEN** `propose` is run against a repo where
  `.github/workflows/dependabot_manifest_check.yml` already exists
- **THEN** `propose` leaves that file untouched and reports it under "skipped"

#### Scenario: Vendored script present but workflow missing
- **WHEN** `propose` is run against a repo that already has
  `scripts/ci/dependabot/dependabot_manifest_check.py` but no
  `.github/workflows/dependabot_manifest_check.yml`
- **THEN** `propose` writes the missing workflow and reports the existing script under "skipped"

#### Scenario: propose --check reports presence without writing
- **WHEN** `propose --check` is run against a repo
- **THEN** the reported state includes whether the manifest-check workflow and the vendored
  script each already exist, and no files are written

### Requirement: scaffolded workflow targets the repo's actual branch model
The scaffolded `dependabot_manifest_check.yml`'s `pull_request` branch triggers SHALL list
exactly the branches `propose` is scaffolding rulesets for (`dev`/`prd` for the 2-branch model,
`dev`/`stg`/`prd` for the 3-branch model), never a hardcoded `main`.

#### Scenario: 2-branch model repo
- **WHEN** `propose` is run with `--branch-model 2` (the default)
- **THEN** the scaffolded workflow's `pull_request.branches` is exactly `[dev, prd]`

#### Scenario: 3-branch model repo
- **WHEN** `propose` is run with `--branch-model 3`
- **THEN** the scaffolded workflow's `pull_request.branches` is exactly `[dev, stg, prd]`

### Requirement: the check runs on every pull request, not only on dependabot.yml diffs
The scaffolded workflow's `pull_request` trigger SHALL NOT be filtered by `paths`. A
directory/manifest mismatch can be introduced by a PR that deletes, renames, or moves a manifest
file without touching `.github/dependabot.yml` at all, so restricting the trigger to
Dependabot-config diffs would miss the common case.

#### Scenario: PR deletes a manifest but not dependabot.yml
- **WHEN** a PR removes the only `pyproject.toml` under a directory that `dependabot.yml`
  configures for the `pip` ecosystem, and does not modify `.github/dependabot.yml`
- **THEN** the manifest check still runs on that PR and fails

#### Scenario: Generated workflow shape
- **WHEN** `propose` writes `dependabot_manifest_check.yml`
- **THEN** the workflow's `pull_request` trigger declares no `paths` or `paths-ignore` key

### Requirement: the check requires no GitHub credentials and makes no API calls
The scaffolded check SHALL operate entirely on the checked-out working tree. It SHALL NOT
require a GitHub App token, `secrets.GITHUB_TOKEN`, or any repository variable or secret, and
SHALL NOT call the GitHub API. A repo with no secrets configured SHALL get a fully functioning
check.

#### Scenario: Workflow generated by propose
- **WHEN** `propose` writes `dependabot_manifest_check.yml`
- **THEN** no step in the workflow references a `secrets.*` or `vars.*` value, and the job needs
  no credential-gated skip path

### Requirement: every checkable ecosystem entry must have a manifest under its directory
The check SHALL parse the target repo's `.github/dependabot.yml` and, for each entry under
`updates` whose `package-ecosystem` appears in a known ecosystem-to-manifest-glob table,
SHALL confirm at least one file matching one of that ecosystem's manifest globs exists directly
within the entry's configured directory. Directories are resolved relative to the repository
root, with `/` meaning the root itself. Glob matching SHALL be non-recursive within the
configured directory — Dependabot itself looks for a manifest at that path, not beneath it.

The initial table SHALL cover at minimum:

| `package-ecosystem` | manifest globs |
|---|---|
| `pip` | `requirements*.txt`, `setup.py`, `pyproject.toml`, `Pipfile` |
| `npm` | `package.json` |

#### Scenario: Configured directory has a matching manifest
- **WHEN** `dependabot.yml` declares `package-ecosystem: pip` with `directory: /` and the
  repository root contains `pyproject.toml`
- **THEN** the check reports success and exits zero

#### Scenario: Configured directory has no matching manifest
- **WHEN** `dependabot.yml` declares `package-ecosystem: pip` with `directory: /tools` and
  `tools/` contains none of `requirements*.txt`, `setup.py`, `pyproject.toml`, or `Pipfile`
- **THEN** the check exits non-zero and its output names the offending ecosystem and the
  configured directory

#### Scenario: Configured directory does not exist
- **WHEN** `dependabot.yml` declares a checkable ecosystem with a `directory` that is not a
  directory in the repository at all
- **THEN** the check exits non-zero and names that ecosystem/directory as having no manifest

#### Scenario: Manifest exists only in a subdirectory of the configured directory
- **WHEN** `dependabot.yml` declares `package-ecosystem: npm` with `directory: /` and the only
  `package.json` in the repository is at `web/package.json`
- **THEN** the check exits non-zero — a manifest nested below the configured directory does not
  satisfy that entry

#### Scenario: Several entries, one broken
- **WHEN** `dependabot.yml` declares three checkable entries and exactly one has no matching
  manifest
- **THEN** the check exits non-zero and its output names that one entry, not the two valid ones

#### Scenario: Omitted directory defaults to the repository root
- **WHEN** a checkable `updates` entry declares no `directory` key
- **THEN** the check evaluates it against the repository root

### Requirement: unrecognized ecosystems are skipped, never failed
An `updates` entry whose `package-ecosystem` is absent from the manifest-glob table SHALL be
skipped without affecting the check's exit status. The table is the explicit allowlist of
ecosystems this check knows how to verify; ecosystems that cannot produce this failure mode
(for example `github-actions`, which scans `.github/workflows/`) and ecosystems not yet mapped
MUST NOT cause a false failure.

#### Scenario: github-actions entry
- **WHEN** `dependabot.yml` declares `package-ecosystem: github-actions` with `directory: /`
- **THEN** the check does not evaluate that entry against any manifest glob and does not fail
  because of it

#### Scenario: Unmapped ecosystem
- **WHEN** `dependabot.yml` declares an ecosystem not present in the table (for example `cargo`)
- **THEN** the check skips that entry and exits zero if every mapped entry is valid

### Requirement: multi-directory entries are checked per directory, with glob patterns skipped
When an `updates` entry uses the plural `directories` key, the check SHALL evaluate each listed
directory independently under the same rule as a single `directory`. A listed value containing
a glob metacharacter SHALL be skipped rather than evaluated literally, because resolving those
patterns is Dependabot's own semantics and a literal-path interpretation would produce a false
failure.

#### Scenario: Explicit directories list, one broken
- **WHEN** an entry declares `package-ecosystem: npm` with `directories: ["/web", "/api"]`,
  `web/package.json` exists, and `api/` contains no `package.json`
- **THEN** the check exits non-zero and names `/api` as the offending directory

#### Scenario: Glob pattern in directories
- **WHEN** an entry declares `directories: ["/apps/*"]`
- **THEN** the check skips that value and does not fail on it

### Requirement: absent or empty Dependabot config is a clean pass
A target repo with no `.github/dependabot.yml`, or one whose config declares no `updates`
entries, SHALL exit zero with a message stating there was nothing to check — never a failure and
never a crash. Config that is not parseable as YAML SHALL exit non-zero with a message naming
the parse error, since an unparseable config is itself a Dependabot misconfiguration.

#### Scenario: No dependabot.yml present
- **WHEN** the check runs in a repo with no `.github/dependabot.yml`
- **THEN** it exits zero and reports that no Dependabot config was found

#### Scenario: Config with no updates entries
- **WHEN** `.github/dependabot.yml` exists but declares an empty or missing `updates` list
- **THEN** the check exits zero and reports that there was nothing to check

#### Scenario: Malformed YAML
- **WHEN** `.github/dependabot.yml` cannot be parsed as YAML
- **THEN** the check exits non-zero and its output names the parse failure

### Requirement: the scaffolded check is not wired into required_status_checks
`propose` SHALL NOT add the manifest-check job's display name to `required_status_checks` in any
generated or existing `.github/rulesets/*.json`. This preserves the existing rule that
`openspec-validate` is the only CI job `propose` promotes to a required check; the manifest check
surfaces as an ordinary failing PR check at review time.

#### Scenario: Fresh repo ruleset generation
- **WHEN** `propose` writes both `dependabot_manifest_check.yml` and a new
  `.github/rulesets/protect-dev.json` in the same run
- **THEN** the generated ruleset's `required_status_checks` contains no entry for the
  manifest-check job

#### Scenario: Existing ruleset files
- **WHEN** `propose` writes `dependabot_manifest_check.yml` into a repo whose
  `.github/rulesets/*.json` files already exist
- **THEN** `propose` does not patch those files to add the manifest-check job
